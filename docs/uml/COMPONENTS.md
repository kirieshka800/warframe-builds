Документ построен по текущему коду и материалам ЛР17. Он содержит две страницы, чтобы разделить зависимости исходных файлов и компоненты собранного приложения.

## Страница 1. Исходный код

Компоненты показаны прямоугольниками с двумя маленькими выступами слева. Каждый блок сопоставлен существующим файлам или группе файлов.

| Компонент | Исходные файлы | Ответственность |
|---|---|---|
| Точка входа | Program.cs | MVC, DI, аутентификация, CSRF, Data Protection, миграции и сидер |
| Контроллеры | Controllers/*.cs; BuildsTransfer.cs — часть BuildsController | HTTP-запросы, проверки прав, валидация и сборка моделей представления |
| Представления | Views/**/*.cshtml | Формирование HTML с помощью Razor |
| Расчёт и подбор | BuildCalculator.cs, ModCompatibility.cs, AutoBuildPlanner.cs | Характеристики, вместимость, совместимость и алгоритм автоподбора |
| Предложения | AutoBuildProposalStore.cs | Краткоживущие предпросмотры в MemoryCache; токены, владелец, TTL |
| Доступ к БД | Data/ApplicationDbContext.cs | DbSet и EF Core-отображение сущностей |
| Модели | Models/*.cs | Сущности и результаты расчётов |
| Синхронизация | Services/WarframeApiService.cs | Загрузка JSON из WFCD через HttpClient и обновление БД |
| Схема и начальные данные | Migrations/*.cs, Services/CatalogSeeder.cs | Миграции и базовый каталог |
| Конфигурация | appsettings*.json, WarframeBuilds.csproj, Dockerfile, compose.yaml | Настройки, пакеты, сборка и запуск |

Это компоненты исходного кода **одного приложения**, а не независимо развёртываемые микросервисы. Расчётные классы не запускаются отдельными процессами и не вызываются по HTTP. На схеме `HomeController.SyncData()` обращается к WarframeApiService; стрелка к нему описана примечанием вместе с несколькими другими зависимостями, чтобы избежать пересечений.

## Страница 2. Сборка и выполнение

Отражены все три вида компонентов из методички:

1. **Рабочие продукты:** исходные `.cs`, Razor `.cshtml`, `.csproj` и Dockerfile.
2. **Компоненты развёртывания:** `WarframeBuilds.dll`, библиотеки .NET/ASP.NET Core/EF Core/Npgsql/Steam, файлы `wwwroot`, ключи Data Protection. Razor-представления при обычном publish компилируются с приложением; они не представлены как отдельный работающий веб-сервер.
3. **Исполняемые компоненты:** хост `dotnet`, запускающий веб-приложение с Kestrel, PostgreSQL и браузер. В Docker фактическая команда запуска — `dotnet WarframeBuilds.dll`. Поэтому вымышленный обязательный `WarframeBuilds.exe` не добавлен: framework-dependent .NET-приложение выполняется хостом dotnet.

`Dockerfile` задаёт .NET 10 и вход `ENTRYPOINT ["dotnet", "WarframeBuilds.dll"]`. `compose.yaml` задаёт web, PostgreSQL 17, привязку `127.0.0.1:5026:8080`, базу `warframe` и постоянные тома `postgres-data` / `app-keys`.

Тома и процессы упомянуты, чтобы пояснить жизненный цикл компонентов. Это не отдельная диаграмма размещения: аппаратные узлы и подробная топология инфраструктуры не моделируются.

## Интерфейсы и зависимости

Окружность на сплошном отрезке обозначает **предоставляемый** интерфейс. Пунктирная стрелка направлена от потребителя к используемому компоненту или интерфейсу.

- **IDisposable** — настоящий C#-интерфейс, который реализует AutoBuildProposalStore; операция Dispose() освобождает MemoryCache.
- **HTTP GET/POST** — контракт веб-компонента с браузером: HTML, формы и статические файлы. Это ASP.NET MVC, не отдельный JSON REST API для всех функций.
- **PostgreSQL wire protocol** — интерфейс PostgreSQL, используемый через EF Core и Npgsql для SQL-запросов.
- **Steam OpenID через HTTPS** — внешний контракт аутентификации Steam, подключённый middleware `.AddSteam()`. Локальные профили существуют отдельно и не требуют Steam.
- **HTTPS GET / JSON** — контракт внешнего каталога WFCD, который использует WarframeApiService при синхронизации.

Названия сетевых контрактов — интерфейсы **компонентов UML**, а не объявления новых C#-интерфейсов `IApi`, `IDatabase` или `IAuthService`. В проекте такие интерфейсы не добавлены. Закомментированные IBuildService/IWarframeApiService на схему не включены.

Кэш предложений — внутренняя память процесса, а не Redis и не отдельный сервер. При перезапуске предложения исчезают; данные PostgreSQL и ключи защиты сохраняются в томах. Билды, моды и гайды хранятся в PostgreSQL, отдельного хранилища аудио или видео в этом проекте нет.

## Соответствие методичке

- Есть компоненты исходного кода, развёртывания и исполнения.
- Указаны реальные имена физических файлов и пакетов.
- Есть предоставляемые интерфейсы и зависимости потребителей.
- Внутренняя структура согласована с диаграммой классов: компоненты расчёта и автоподбора содержат соответствующие статические классы; контроллеры обращаются к ним и DbContext.
- Пример диаграммы другого приложения использован как образец обозначений, его функции и технологии не перенесены в warframe-builds.

Основания: `WarframeBuilds/Program.cs`, `WarframeBuilds/WarframeBuilds.csproj`, `Dockerfile`, `compose.yaml`, файлы Controllers/Services/Data. Код сверен с main `bca7cf7ccdfdc1161ef62e0864633868e4ff8381`; в этом коммите последние изменения затрагивали только документацию UML.
